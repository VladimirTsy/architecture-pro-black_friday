**Проект:** Онлайн-магазин «Мобильный мир» (Масштабирование)  
**Автор:** Системный архитектор  
**Файл:** `Task_7_SHARDING_ARCH.md`

## 1. Введение и Обоснование архитектурных решений

С расширением ассортимента онлайн-магазина «Мобильный мир» (включение бытовой, аудио- и электронной техники) нагрузка на базу данных возрастает экспоненциально. Одиночные инстансы СУБД перестают удовлетворять требованиям по доступности и скорости ответа. Для решения этой проблемы спроектирована горизонтально масштабируемая архитектура на базе **шардированного кластера MongoDB с репликацией каждого шарда**.

### Ключевые архитектурные принципы:
1. **Stateless-бэкенд с API Gateway:** Входящий трафик балансируется по алгоритму Round Robin между изолированными инстансами приложения.
2. **Service Discovery (Consul):** Динамический учет инстансов и контроль их здоровья (Health Check) для исключения простоев.
3. **Кеширование (Redis):** Быстрое чтение популярных эндпоинтов в обход обращений к СУБД (время отклика повторных вызовов `< 100мс`).
4. **Отказоустойчивость СУБД:** Каждый шард представляет собой реплика-сет (1 Primary + 2 Secondary ноды) с автоматическим выбором лидера при сбоях (Heartbeat-интервал 2 секунды).

## 2. Структуры данных и Схемы коллекций

Ниже представлены структуры документов для трех основных коллекций: `products`, `orders` и `carts`.

### 2.1. Коллекция `products` (Товары)
* **Нагрузка:** Высокая частота чтения (просмотр каталога, поиск, фильтрация) и частые точечные обновления остатков товаров в разрезе регионов при покупках.

```json
{
  "_id": "ObjectId",
  "name": "String",
  "category": "String",
  "price": "Double",
  "geo_stocks": {
    "moscow": "Int32",
    "ekaterinburg": "Int32",
    "kaliningrad": "Int32"
  },
  "attributes": {
    "color": "String",
    "size": "String"
  },
  "created_at": "ISODate"
}
```

### 2.2. Коллекция `orders` (Заказы)
* **Нагрузка:** Интенсивная линейная запись при создании новых заказов, поиск истории заказов конкретного пользователя, точечные обновления статуса доставки.

```json
{
  "_id": "ObjectId",
  "user_id": "String",
  "created_at": "ISODate",
  "items": [
    {
      "product_id": "ObjectId",
      "quantity": "Int32",
      "price": "Double"
    }
  ],
  "status": "String",
  "total_amount": "Double",
  "geo_zone": "String"
}
```

### 2.3. Коллекция `carts` (Корзины)
* **Нагрузка:** Интенсивная запись и обновление. Быстрые выборки активных корзин авторизованных пользователей по `user_id` или гостей по `session_id`. Автоматическая очистка старых документов.

```json
{
  "_id": "ObjectId",
  "user_id": "String (nullable)",
  "session_id": "String (nullable)",
  "items": [
    {
      "product_id": "ObjectId",
      "quantity": "Int32"
    }
  ],
  "status": "String",
  "created_at": "ISODate",
  "updated_at": "ISODate",
  "expires_at": "ISODate"
}
```

## 3. Выбор Shard-ключей и Стратегий шардирования

| Коллекция | Выбранный Shard-ключ | Стратегия шардирования | Преимущества | Риски и их минимизация |
| :--- | :--- | :--- | :--- | :--- |
| **products** | `category` | **Шардирование по диапазонам (Ranged)** | Поиск товаров по категориям и фильтрация по ценам локализуются на конкретном шарде. Позволяет избежать операции Scatter-Gather при чтении каталога. | *Риск:* Неравномерный размер шардов, если одна категория сильно популярнее остальных. *Минимизация:* Использование составного ключа `{ category: 1, _id: 1 }` для равномерного дробления чанков. |
| **orders** | `{ user_id: "hashed" }` | **Хэшированное шардирование (Hashed)** | Обеспечивает абсолютно равномерное распределение операций записи новых заказов по всем шардам кластера. Запрос истории заказов конкретного пользователя отрабатывает за одно целевое чтение. | *Риск:* Аналитические запросы (например, отчеты по продажам в конкретной геозоне за месяц) пойдут на все шарды. *Минимизация:* Выполнение аналитических агрегаций на изолированных вторичных (`Secondary`) репликах. |
| **carts** | `{ session_id: "hashed" }` или `{ user_id: "hashed" }` | **Хэшированное шардирование (Hashed)** | Гарантирует отсутствие "горячих точек" при пиковых нагрузках (например, в Черную Пятницу). Временные корзины равномерно распределяются по кластеру. | *Риск:* Операция слияния корзины гостя с корзиной пользователя при логине потребует чтения и записи на разных шардах. *Минимизация:* За счет хэширования точечные операции поиска `_id` выполняются мгновенно, нивелируя сетевой оверхед. |

## 4. Конфигурация кластера и Примеры команд (MongoDB Shell)

### 4.1. Включение шардирования для базы данных
Выполняется один раз на роутере `mongos`:
```javascript
sh.enableSharding("somedb");
```

### 4.2. Шардирование коллекции `products`
Создаем составной индекс и разбиваем коллекцию по диапазонам категорий:
```javascript
use somedb;
db.products.createIndex({ category: 1, _id: 1 });
sh.shardCollection("somedb.products", { category: 1, _id: 1 });
```

### 4.3. Шардирование коллекции `orders`
Создаем хэшированный индекс по идентификатору пользователя для равномерного распределения записи:
```javascript
use somedb;
db.orders.createIndex({ user_id: "hashed" });
sh.shardCollection("somedb.orders", { user_id: "hashed" });
```

### 4.4. Шардирование коллекции `carts` и настройка автоочистки (TTL)
Шардируем временные данные по сессии и создаем специальный TTL-индекс для автоматического удаления брошенных корзин:
```javascript
use somedb;
db.carts.createIndex({ session_id: "hashed" });
sh.shardCollection("somedb.carts", { session_id: "hashed" });

// Создание TTL-индекса (MongoDB автоматически удалит документ, как только текущее время превысит expires_at)
db.carts.createIndex({ "expires_at": 1 }, { expireAfterSeconds: 0 });
```

## 5. Метрики мониторинга и План реагирования при сбоях

Для упреждающего контроля производительности инфраструктуры «Мобильный мир» настраивается стек Prometheus + Grafana со сбором следующих метрик.

### Ключевые метрики:
1. **Chunk Distribution Balance:** Разница в количестве чанков (данных) между шардами. Сигнализирует о перекосе данных.
2. **Scatter-Gather Ratio:** Процент запросов без шард-ключа, опрашивающих все ноды подряд (метрика должна быть близка к нулю).
3. **Replication Lag:** Время отставания нод `Secondary` от `Primary` в секундах (критично для консистентности чтения со вторичных узлов).
4. **Cache Hit Ratio (Redis):** Эффективность кэширования. Падение ниже 85% означает резкое возрастание нагрузки на СУБД.
5. **Operation Latency (p99):** Время выполнения тяжелых запросов записи и чтения на шардах.

### План действий при инцидентах:

* **Инцидент: Неравномерная нагрузка / Один из шардов переполнен**
  * *Причина:* "Jumbo Chunks" — скопление документов с одинаковым значением шард-ключей низкой кардинальности.
  * *Решение:* Запустить ручной балансировщик `sh.startBalancer()`. В случае невозможности разделения чанка произвести процедуру уточнения шард-ключа (`refineCollectionShardKey`), добавив уникальный суффикс (например, `_id`).
* **Инцидент: Высокий Replication Lag на узлах шарда**
  * *Причина:* Медленный дисковый ввод-вывод (`I/O`) на репликах или перегрузка Secondary-нод тяжелыми аналитическими запросами.
  * *Решение:* Запретить выполнение аналитики на стандартных репликах, переведя её на скрытые (`Hidden`) ноды. Выполнить апгрейд дисковой подсистемы до NVMe.
* **Инцидент: Падение общей скорости работы сайта (Таймауты)**
  * *Причина:* Инвалидация или вытеснение данных из оперативной памяти Redis (Cache Hit Ratio упал), СУБД перегружена.
  * *Решение:* Выделить больше ресурсов оперативной памяти для Redis, изменить политику вытеснения ключей на `allkeys-lru` (удаление наименее используемых).
