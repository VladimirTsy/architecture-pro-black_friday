## 1. Матрица распределения операций чтения (Primary vs Secondary)

Для снижения нагрузки на мастер-узлы (`Primary`) и эффективного использования ресурсов реплика-сетов шардов, операции чтения распределяются в соответствии с требованиями бизнес-логики и критичности к актуальности данных:

| Коллекция | Конкретная операция чтения | Узел для чтения (`Read Preference`) | Допустимый лаг репликации (`Max Lag`) | Обоснование и бизнес-риски |
| :--- | :--- | :--- | :--- | :--- |
| **products** | Просмотр карточки товара, описания, характеристик, атрибутов. | `secondaryPreferred` | **До 5–10 секунд** | Статическое описание товаров и характеристики меняются редко. Чтение устаревших атрибутов на пару секунд не несет финансовых рисков. |
| **products** | Поиск товаров по категориям и фильтрация по ценам. | `secondaryPreferred` | **До 5–10 секунд** | Каталог генерирует огромный поток чтений. Допустимо кратковременное отображение старого списка товаров для разгрузки Primary-нод. |
| **products** | Проверка и обновление остатков товара в геозоне при покупке. | `primary` | **0 секунд (Strict)** | **Критическая операция.** Чтение с Secondary создаст высокий риск продажи товара, которого нет в наличии (Overselling), что ведет к отказам и репутационным потерям. |
| **orders** | Отображение статуса заказа и истории для пользователя. | `primary` | **0 секунд (Strict)** | Сразу после создания или оплаты заказа клиент ожидает увидеть статус `"Оплачен"` или `"В сборке"`. Устаревший статус вызовет панику и лавину тикетов в поддержку. |
| **orders** | Поиск истории старых (архивных) заказов пользователя. | `secondaryPreferred` | **До 30 секунд** | Исторические данные статичны. Задержка в отображении только что созданного заказа в общем списке на несколько секунд приемлема. |
| **carts** | Получение текущей активной корзины (`status: "active"`). | `primary` | **0 секунд (Strict)** | Пользователь непрерывно меняет состав корзины. Чтение с реплики с задержкой приведет к рассинхронизации: удаленные товары могут снова появиться в корзине. |
| **carts** | Чтение гостевой корзины при слиянии и авторизации. | `primary` | **0 секунд (Strict)** | Процесс слияния items гостевой сессии в пользовательскую требует атомарности и точных данных в момент выполнения операции, чтобы избежать дублирования. |

## 2. Обоснование допустимых задержек репликации и уровней Read Concern

Для контроля задержек на узлах репликации используется встроенный механизм драйвера MongoDB **`maxStalenessSeconds`**. Он автоматически запрещает роутерам `mongos` перенаправлять запросы на те `Secondary`-ноды, чье отставание от лидера превышает установленный лимит.

### 2.1. Строгая консистентность (Линейная согласованность)
Для критичных к консистентности операций (списание остатков товаров, управление активными корзинами, обновление транзакционных статусов заказов) используется чтение с **Primary** узлов в сочетании с гарантиями записи:
* **Read Concern:** `"linearizable"` или `"local"`
* **Write Concern:** `"majority"`
* **Бизнес-эффект:** Исключает феномен "грязного чтения" (Dirty Reads) и чтение откатившихся данных в случае перевыборов Primary-ноды при возникновении сетевого сплита (Split-brain).

### 2.2. Ослабленная консистентность (Eventual Consistency)
Для операций массового чтения (каталог товаров, поиск, архивные данные) чтение делегируется на **Secondary** узлы:
* **Read Concern:** `"local"`
* **Конфигурация подключения:** `maxStalenessSeconds = 90`
* **Бизнес-эффект:** Если нода Secondary отстает от лидера более чем на 1.5 минуты из-за высокой дисковой нагрузки, `mongos` временно убирает ее из пула балансировки чтения, исключая отдачу клиентам критически устаревших данных.

## 3. Примеры конфигурации команд в приложении (Python / pymongo)

Примеры демонстрируют, как бэкенд-приложение `pymongo_api` переключает параметры консистентности на уровне драйвера.

### 3.1. Чтение каталога товаров с реплик (Secondary)
```python
from pymongo import MongoClient
from pymongo.read_preferences import SecondaryPreferred

# Инициализация клиента с ограничением на максимальный лаг репликации в 10 секунд
client = MongoClient("mongodb://mongos-1:27017,mongos-2:27017/?maxStalenessSeconds=10")
db = client.somedb

# Запрос карточки товара с реплики для разгрузки мастер-узла
product = db.products.with_options(read_preference=SecondaryPreferred()).find_one(
    {"_id": product_id}
)
```

### 3.2. Атомарная проверка и обновление остатков (Strict Primary)
```python
from pymongo.read_concern import ReadConcern
from pymongo.write_concern import WriteConcern

# Настройка коллекции для транзакционной работы строго на Primary с мажоритарной записью
coll_products = db.products.with_options(
    read_concern=ReadConcern("local"),
    write_concern=WriteConcern("majority")
)

# Атомарное списание остатка в конкретной геозоне
result = coll_products.update_one(
    {"_id": product_id, "geo_stocks.moscow": {"\$gte": quantity}},
    {"\$inc": {"geo_stocks.moscow": -quantity}}
)
```
