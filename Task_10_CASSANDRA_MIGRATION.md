## 1. Анализ данных и обоснование миграции (Задание 10.1)

В условиях экстремальной нагрузки (50 000+ RPS) в Черную Пятницу Range-Based шардирование в MongoDB показало свою неэффективность при масштабировании «на лету» из-за тяжелого процесса перемещения чанков (Data Balancing). Для обеспечения высокой доступности и линейного горизонтального масштабирования была проведена классификация данных интернет-магазина:

### 1.1. Классификация данных
1. **Заказы (Orders) и История заказов:** Критически важны. Требуют сверхбыстрой append-only записи, надежного сохранения транзакционных данных и быстрого извлечения истории по конкретным пользователям.
2. **Товары и Остатки (Products & Stocks):** Требуют высокой консистентности (ACID/строгая согласованность) для исключения оверселлинга (продажи недоступного товара), частых точечных обновлений остатков `In-Place`.
3. **Корзины и Сессии пользователей (Carts & Sessions):** Высокоинтенсивный поток короткоживущих операций записи/чтения/обновления с жесткими требованиями к минимальной задержке (Latency).

### 1.2. Обоснование выбора Apache Cassandra
Применение Apache Cassandra экономически и технически оправдано для **Заказов (`orders`)** и **Корзин/Сессий пользователей (`carts`)** по следующим причинам:
* **Линейное масштабирование без решардинга:** Благодаря использованию согласованного хэширования (Consistent Hashing) и виртуальных узлов (Vnodes) при добавлении нового сервера в кольцо Cassandra данные перераспределяются **только** с соседних узлов. Полного перемещения данных всего кластера (как в MongoDB) не происходит, что предотвращает просадку latency в пик нагрузки.
* **Leaderless-архитектура:** Отсутствие единой точки отказа (no single point of failure) позволяет принимать запись на любой узел кластера, гарантируя бесперебойный прием заказов в Черную Пятницу, даже если часть серверов выйдет из строя.
* **Оптимизация под запись (LSM-Tree):** Cassandra выполняет запись последовательно в Memtable и CommitLog (без случайного поиска по диску), что обеспечивает минимальный latency на запись при 50 000+ RPS.

> **Важно (Архитектурное ограничение):** Коллекцию **товаров (`products`)** со сложными реляционными фильтрами по ценам, атрибутам и жестким требованиям к атомарному обновлению остатков («списание») **целесообразно оставить в реплицированном кластере MongoDB** (или перенести в специализированную РСУБД/НьюБД), так как Cassandra плохо справляется с точечными апдейтами числовых полей и не поддерживает сложные многокритериальные индексы.

## 2. Концептуальная модель данных и минимизация "горячих" партиций (Задание 10.2)

Моделирование в Cassandra строится по принципу *Query-Driven Design* (одна таблица под один тип запроса). Ниже представлены структуры таблиц на языке CQL (Cassandra Query Language).

### 2.1. Таблица заказов (`orders_by_user`)
* **Целевой запрос:** Быстрый поиск истории заказов конкретного пользователя, отсортированный по дате от новых к старым.

```sql
CREATE KEYSPACE mobile_world_store 
WITH replication = {'class': 'NetworkTopologyStrategy', 'datacenter1': 3};

USE mobile_world_store;

CREATE TABLE orders_by_user (
    user_id text,
    order_date timestamp,
    order_id uuid,
    geo_zone text,
    items text, -- Сериализованный JSON со списком товаров
    status text,
    total_amount double,
    PRIMARY KEY ((user_id), order_date, order_id)
) WITH CLUSTERING ORDER BY (order_date DESC, order_id ASC);
```
* **Разбор ключа:**
  * **Partition Key:** `user_id`. Хэш от идентификатора пользователя определяет, на какой узел попадет строка. Это гарантирует абсолютно равномерное распределение данных по кольцу кластера (нет горячих шардов по категориям).
  * **Clustering Key:** `order_date`, `order_id`. Внутри партиции пользователя данные физически упорядочены по дате по убыванию (`DESC`). Запрос истории заказов выполняется за одну дисковую операцию последовательного чтения.

### 2.2. Таблица активных корзин (`active_carts`)
* **Целевой запрос:** Мгновенное чтение/обновление состава корзины по сессии или пользователю с автоматическим временем жизни (TTL).

```sql
CREATE TABLE active_carts (
    cart_lookup_id text, -- Хэш от user_id или session_id (для гостей)
    product_id uuid,
    quantity int,
    updated_at timestamp,
    PRIMARY KEY ((cart_lookup_id), product_id)
) WITH default_time_to_live = 86400; -- Автоматическая очистка старых корзин через 24 часа
```
* **Разбор ключа:**
  * **Partition Key:** `cart_lookup_id`. Равномерно размывает миллионы корзин покупателей по всем узлам. Полностью исключает риски образования «горячих» партиций, так как данные одного пользователя никогда не превысят размер одной партиции (лимит в 100-200 МБ).

## 3. Стратегии обеспечения целостности данных и компромиссы (Задание 10.3)

Cassandra следует принципам **BASE** и **CAP-теореме (выбор в пользу AP)**. Для настройки баланса между скоростью ответа (Latency) и согласованностью данных (Consistency) применяются три базовые стратегии:

### 3.1. Hinted Handoff (Срочная недоставка)
* **Как работает:** Если целевой узел, отвечающий за запись, временно недоступен (сетевой сбой), узел-координатор сохраняет локальную подсказку (Hint) и пересылает её, как только целевой узел вернется в строй.
* **Выбор для сущностей:** Включается **для всех таблиц (`orders_by_user`, `active_carts`)** на системном уровне.
* **Обоснование:** Позволяет кластеру бесперебойно принимать заказы и добавления в корзину от клиентов при кратковременном падении отдельных серверов, гарантируя отказоустойчивость записи (High Availability).

### 3.2. Read Repair (Восстановление при чтении)
* **Как работает:** При чтении координатор сравнивает контрольные суммы данных с нескольких реплик. Если обнаружено расхождение, клиенту отдается самая свежая запись (по timestamp), а на отстающий узел в фоновом режиме отправляется команда обновления.
* **Выбор для сущностей:** Настраивается коэффициент фонового восстановления `read_repair_chance = 0.1` **для истории заказов** (`orders_by_user`).
* **Обоснование:** Для архивной истории заказов микроскопический лаг согласованности не критичен, а фоновый ремонт позволяет поддерживать реплики в актуальном состоянии без создания паразитной нагрузки на сеть в момент записи.

### 3.3. Anti-Entropy Repair (Антиэнтропийное восстановление / nodetool repair)
* **Как работает:** Тяжелая запланированная процедура синхронизации данных между узлами на основе сравнения деревьев Меркла (Merkle Trees). Выявляет скрытые расхождения, которые были пропущены из-за переполнения Hinted Handoff.
* **Выбор для сущностей:** Запускается по регламенту раз в неделю в часы минимальной нагрузки (ночью) **для всех данных**.
* **Обоснование:** Гарантирует итоговую согласованность (Eventual Consistency) распределенной системы в долгосрочной перспективе, полностью исключая накопление расхождений между дата-центрами.

### 3.4. Тюнинг уровней согласованности (Компромисс CAP)

Для достижения оптимального баланса Latency / Consistency на уровне выполнения CQL-запросов устанавливаются следующие параметры:

* **Для Корзин (`active_carts`):**
  * *Запись:* `LOCAL_ONE` / *Чтение:* `LOCAL_ONE`.
  * *Обоснование:* Максимальный приоритет скорости (минимальный Latency). Если пользователь увидит старый состав корзины на долю секунды — это допустимый бизнес-компромисс ради мгновенного отклика интерфейса.
* **Для Заказов (`orders_by_user`):**
  * *Запись:* `LOCAL_QUORUM` / *Чтение:* `LOCAL_QUORUM`.
  * *Обоснование:* Обеспечивает **Строгую согласованность (Strong Consistency)**, так как сумма кворумов чтения и записи строго больше фактора репликации ($R + W > N$). Клиент гарантированно прочитает самую актуальную информацию о своем только что созданном заказе, при этом задержка остается низкой, так как опрашивается кворум только внутри одного (локального) дата-центра.

## Приложение А. Глоссарий используемых архитектурных терминов

В ходе проектирования целевой топологии базы данных и анализа ограничений мигрируемых сущностей используются следующие классы систем управления базами данных (СУБД):

### 1. РСУБД (Реляционные системы управления базами данных)
Классические системы, основанные на реляционной модели данных, где информация хранится в виде строго структурированных таблиц с предопределенными связями (Foreign Keys).
* **Примеры:** PostgreSQL, MySQL, Oracle.
* **Преимущества:** Полная и бескомпромиссная поддержка **ACID-транзакций** (атомарность, согласованность, изолированность, долговечность). Гарантируют железную консистентность данных «в любой момент времени» (Strong Consistency).
* **Применение в проекте:** Рекомендуются для хранения остатков товаров и проведения складских списаний, где недопустим малейший риск рассинхронизации данных.
* **Недостатки:** Сложность и высокий оверхед при попытке горизонтального масштабирования (шардирования) на запись под экстремальными нагрузками.

### 2. НьюБД (NewSQL)
Современный класс систем управления базами данных, призванный объединить преимущества NoSQL-систем (линейное горизонтальное масштабирование) и классических РСУБД (транзакционность и поддержка языка SQL).
* **Примеры:** CockroachDB, Google Spanner, YugabyteDB, TiDB.
* **Преимущества:** Автоматическое распределение данных по узлам кластера (автошардирование) без потери поддержки распределенных ACID-транзакций. Отсутствие единой точки отказа при сохранении привычной реляционной модели данных.
* **Применение в проекте:** Рассматриваются как перспективный целевой стек для эволюции сервиса товаров (`products`) в случае деградации производительности текущего шардированного кластера MongoDB.
