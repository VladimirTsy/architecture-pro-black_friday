## 1. Разработка аналитических метрик мониторинга дисбаланса (PromQL)

Стандартные счетчики `mongodb_exporter` по отдельности не показывают состояние перекоса. Для упреждающего обнаружения «горячих» шардов разработаны следующие составные аналитические метрики и правила фильтрации в Prometheus/Grafana:

### 1.1. Коэффициент дисбаланса IOPS по шардам (Shard IOPS Imbalance Ratio)
* **Как создается (Формула PromQL):**
  Мы берем скорость роста операций (интенсивность запросов) на конкретном шарде и делим её на сумму скоростей операций по всему кластеру, переводя в проценты:
  ```promql
  (
    sum by (shard) (rate(mongodb_op_counters_total{type=~"query|insert|update"}[5m]))
    / 
    sum(rate(mongodb_op_counters_total{type=~"query|insert|update"}[5m]))
  ) * 100
  ```
* **Бизнес-логика alert-триггера:** Если значение для любого `shard` превышает **70%** в течение 10 минут, Grafana отправляет критический алерт `HotShardOperationOverload`.

### 1.2. Метрика неравномерности распределения данных (Data Storage Skew)
* **Как создается (Формула PromQL):**
  Вычисляется отклонение физического размера данных конкретного инстанса шарда от среднего значения объема данных по всему кластеру:
  ```promql
  (
    mongodb_db_share_data_size_bytes 
    - 
    avg without(instance) (mongodb_db_share_data_size_bytes)
  ) / avg without(instance) (mongodb_db_share_data_size_bytes) * 100
  ```
* **Бизнес-логика alert-триггера:** Превышение порога в **+20%** на любом шарде при включенном балансировщике свидетельствует об образовании неделимых крупных чанков (Jumbo Chunks), которые СУБД не может распределить автоматически.

### 1.3. Коэффициент утилизации WiredTiger тикетов (WiredTiger Ticket Saturation)
* **Как создается (Формула PromQL):**
  Метрика отслеживает процент исчерпания параллельных потоков чтения/записи на каждом шарде (сколько тикетов занято из максимально доступных 128 по умолчанию):
  ```promql
  (
    1 - (
      mongodb_wiredtiger_concurrent_transactions_available{type=~"read|write"} 
      / 
      mongodb_wiredtiger_concurrent_transactions_max{type=~"read|write"}
    )
  ) * 100
  ```
* **Бизнес-логика alert-триггера:** Если утилизация тикетов держится на уровне **> 90%** дольше 2 минут только на одном шарде, это подтверждает, что узел находится под жестким троттлингом из-за наплыва запросов к горячей категории.

### 1.4. Индекс концентрации клиентских сессий (Session Concentration Index)
* **Как создается (Формула PromQL):**
  Показывает процентное распределение активных сетевых соединений от роутеров к инстансам:
  ```promql
  (mongodb_connections{state="current"} / on() group_left sum(mongodb_connections{state="current"})) * 100
  ```
* **Бизнес-логика alert-триггера:** Алерт срабатывает, если один узел удерживает более **65%** всех открытых клиентских сессий кластера, что предвещает скорое исчерпание лимита `maxConnections`.

## 2. Механизмы автоматического и ручного устранения дисбаланса

В СУБД MongoDB стратегия шардирования по диапазонам (Ranged Sharding) для коллекции `products` по ключу `{ category: 1 }` привела к тому, что все товары популярной категории «Электроника» (70% запросов) попали в один или несколько смежных чанков на одном шарде. Так как кардинальность значения поля `category` низкая, стандартный балансировщик не может автоматически разделить или перенести эти данные.

Для устранения возникшего перекоса применяются следующие архитектурные механизмы:

### Метод 1. Динамическое уточнение шард-ключа (Refine Shard Key) — Основное решение
Начиная с MongoDB 4.4, можно изменить шард-ключ «на лету», добавив к нему суффиксное поле с высокой кардинальностью (например, уникальный идентификатор товара `_id`). Это позволит СУБД дробить чанки внутри одной категории («Электроника») и равномерно распределять их по всем шардам кластера.

**Пример команд в MongoDB Shell:**
```javascript
use somedb;

// 1. Создаем новый поддерживающий составной индекс на всех узлах шарда
db.products.createIndex({ category: 1, _id: 1 });

// 2. Уточняем существующий шард-ключ, добавляя к нему поле _id
sh.refineCollectionShardKey("somedb.products", { category: 1, _id: 1 });
```

### Метод 2. Разделение и ручной перенос чанков (Jumbo Chunks Mitigation)
Если чанк с электроникой стал слишком большим (превысил 64 МБ) до изменения ключа, он помечается флагом `jumbo`, и балансировщик перестает его обрабатывать. Такой чанк необходимо разделить вручную на основе диапазона идентификаторов и перенести на менее загруженный шард из системной базы `admin`.

**Пример команд в MongoDB Shell:**
```javascript
use admin;

// 1. Принудительно делим гигантский чанк категории "Электроника" пополам по значению _id
sh.splitFind("somedb.products", { category: "Электроника", _id: ObjectId("6aeedc500000000000000000") });

// 2. Убеждаемся, что автоматический балансировщик включен для миграции новых чанков
sh.startBalancer();

// 3. (Опционально) Если нужно немедленно разгрузить узел, переносим чанк вручную на Шард-2
sh.moveChunk("somedb.products", { category: "Электроника", _id: ObjectId("6aeedc500000000000000000") }, "shard2ReplSet");
```

### Метод 3. Двухуровневое хэширование на уровне приложения (Изоляция топ-категорий)
Если бизнес-требования не позволяют менять шард-ключ в СУБД, защита реализуется на уровне бэкенда. Для самой горячей категории («Электроника») вводится суффикс-балансировщик. 

При записи нового товара вместо категории `"Электроника"` приложение подставляет строку `"Электроника_1"`, `"Электроника_2"`, ..., `"Электроника_N"` (вычисляется как `hash(product_id) % N`). Для MongoDB это будут разные категории, и их чанки гарантированно разойдутся по разным шардам кластера. При поиске по категории бэкенд выполнит параллельные запросы по этим подкатегориям.

## 3. Регламент действий дежурного инженера при инциденте `Hot_Shard`

При срабатывании триггера оповещения `Shard_IOPS_Imbalance (Ratio > 70%)` инженер обязан:
1. Выполнить команду `sh.status()` на роутере `mongos` и проверить систему на наличие зависших миграций или чанков со статусом `jumbo`.
2. Запустить команду `db.currentOp()` на «горячем» шарде для выявления неоптимизированных тяжелых запросов чтения или долгих блокировок.
3. Проверить `Cache Hit Ratio` в Redis. Если эффективность кэширования упала ниже 85%, восстановить работу кэша бэкенда, чтобы снять паразитную нагрузку на чтение с СУБД.
4. Запланировать применение процедуры **`refineCollectionShardKey`** (Метод 1) в ближайшее технологическое окно для окончательного устранения архитектурного дисбаланса.
